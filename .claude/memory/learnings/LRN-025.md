# LRN-025 — `defer` vs `patch` en bmad-code-review : JSDoc sur interface publique = patch non-ambigu

| Pattern observé                                                                                                         | Contexte                                                                                                | Application future                                                                                                                       |
| ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Un ajout de JSDoc sur une interface publique est un `patch` (fix non-ambigu, applicable immédiatement) — pas un `defer` | Session `/bmad-code-review` Story 1.2 — D1/D3/D4/D5 initialement classés `defer`, corrigés par Baptiste | Lors du triage : si le fix ne dépend d'aucune story future, donnée externe, ou décision architecturale → classifier `patch`, pas `defer` |

## Détail

Un `defer` est réservé aux findings qui nécessitent genuinement :

- une story dédiée (implémentation non triviale)
- des données externes (ex. spritesheets réelles pour STATE_MAPPING)
- une décision architecturale (ex. quel format pour `compatibleWith`)

Un `patch` = tout fix non-ambigu applicable dans la session courante, y compris :

- JSDoc documentant un contrat de plage, un format attendu, une précondition
- Correction de typo ou de naming
- Ajout d'un `readonly`, d'un `as const`, d'une assertion triviale

Les 4 JSDoc appliqués sur `src/types.ts` lors de cette session (`compatibleWith`, `progress 0-1`, `Buffer non-vide`, `path absolu`) auraient dû être des patches dès la première passe.
