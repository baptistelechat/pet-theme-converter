# LRN-031 — fetch() natif : vérifier `response.ok` avant Content-Type pour typer correctement FetchError vs ValidationError

| Pattern observé                                                                                                                                                                                                                 | Contexte                                                  | Application future                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Sans check `response.ok`, une URL 404 retourne `text/html` → déclencherait `ValidationError` au lieu de `FetchError`. L'ordre correct : `!response.ok` → `FetchError` d'abord, puis Content-Type non-image → `ValidationError`. | Story 2.1 — conception du skeleton `fetch-spritesheet.ts` | Toute fonction Core faisant un `fetch()` avec validation de Content-Type dans ce projet |

## Détail

La séquence correcte dans le `try` d'un `fetch()` avec erreurs typées :

```ts
const response = await fetch(url, { signal: controller.signal });

// 1. URL inaccessible (non-2xx) → FetchError
if (!response.ok) {
  throw new FetchError(`URL inaccessible (HTTP ${response.status}) : ${url}`);
}

// 2. URL accessible mais mauvais format → ValidationError
const contentType = response.headers.get("content-type") ?? "";
if (!contentType.startsWith("image/")) {
  throw new ValidationError(`Content-Type non supporté : "${contentType}"`);
}
```

Et dans le `catch`, toujours re-lancer les erreurs typées en premier :

```ts
} catch (err) {
  if (err instanceof FetchError || err instanceof ValidationError) throw err;
  // ... AbortError, fallback générique
}
```

Sans le re-lancer en premier, les erreurs typées lancées dans le `try` seraient enveloppées dans un `FetchError` générique → perte du type et du message d'origine.
